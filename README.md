# 精密试验场授时网络规划台

纯前端（TypeScript + React）授时网络规划工具：工程师在页面编辑或导入节点、主钟与候选有向链路，
一键计算**总代价最小的有向生成树**，查看每台从钟的父链路、到主钟的完整路径与累计代价。
全部业务计算在本地浏览器完成，无任何后端依赖。

## 业务模型与约束

| 约束 | 说明 |
| --- | --- |
| 节点 | 2 ~ 40 个，名称唯一、非空 |
| 主钟 | 必须是指定节点之一；主钟不选择入边 |
| 候选链路 | 1 ~ 120 条，编号为唯一正整数 |
| 链路端点 | 必须存在于节点列表且起点 ≠ 终点（不允许自环） |
| 安装代价 | 正整数（安全整数范围内，合计以 BigInt 精确求和） |
| 可行性 | 主钟以外每个节点恰选一条入边，且全部由主钟可达 |

- **字段错误**：点击「开始计算」后一次性定位反馈全部错误（节点行 / 链路行同步高亮）。
- **结构合法但不可覆盖**：明确列出从主钟在候选图中不可达的节点。
- **成功结果**：总代价、选中链路编号（升序）、每台从钟的父链路与到主钟路径；
  点选任一从钟可逐段核对路径与累计代价。
- **结果失效**：任何输入修改立即使旧结果失效。

## 全局裁决算法（非逐节点贪心）

逐台选择最便宜链路会在节点间成环（例如 A←B、B←A 互为最便宜），使部分设备永远无法追溯到主钟。
本工具使用 **Chu-Liu/Edmonds 最小树形图算法**（`src/core/edmonds.ts`）做全局最优裁决：

1. 每个非根节点取最小入边；无环即收敛；
2. 有环则收缩为超节点，入环边权重减去环内目标点最小入边权，递归求解后展开。

**同代价裁决**：要求选中链路编号的升序数组字典序最小。实现上将每条链路权重编码为复合
`bigint`：

```
W = cost · 2^(m+8) − 2^(m − rank(id))
```

`rank(id)` 为编号升序名次（1..m）。高位段保证总代价优先；低位段是「小编号权重更大」的超递增
扰动——等大小的两个解集合比较扰动和时，对称差中最小编号所在的一方恒胜，即编号升序数组字典序
最小。由于全程使用 `bigint` 精确运算，该编码不引入任何精度误差，一次求解即得全局裁决结果，
而非逐节点贪心的事后修补。

正确性由 `tests/solve.test.ts` 中的**暴力枚举对拍**保障：600 组随机小规模模型下，
Edmonds 结果的代价与编号字典序均与穷举全部生成树的最优解完全一致。

## 本地开发

```bash
npm ci            # 安装依赖
npm run dev       # 开发服务器
npm run test      # 单元测试（vitest，含暴力对拍）
npm run build     # 类型检查 + 生产构建（输出 dist/）
npm run smoke     # 对 dist/ 做静态站点 HTTP 冒烟
npm run verify    # 测试 + 构建 + 冒烟 一键验证
```

## 导入格式

页面支持粘贴 JSON 文本或选择 JSON 文件导入（亦可导出当前输入）：

```json
{
  "nodes": ["主钟GPS", "从钟A", "从钟B"],
  "master": "主钟GPS",
  "links": [
    { "id": 1, "from": "主钟GPS", "to": "从钟A", "cost": 10 },
    { "id": 2, "from": "从钟A", "to": "从钟B", "cost": 3 }
  ]
}
```

兼容常见字段别名（`edges`/`source`/`target`/`weight` 等）；字段值合法性由统一校验器一次性反馈。

## Docker 交付

### 构建并运行静态站点

```bash
docker build -t timing-network-planner .      # 默认目标即 app（nginx 静态站点）
docker run -d -p 8080:80 timing-network-planner
```

镜像内置 `HEALTHCHECK`（探测 `/healthz`）。

### Docker Compose

```bash
# 启动站点（宿主机端口可配置，默认 8080）
APP_PORT=9000 docker compose up -d app

# 查看健康状态
docker compose ps

# 一次性验证：代码测试 → 生产构建 → 静态站点 HTTP 冒烟
# 容器执行完毕自行退出，退出码即验证结果（0 通过，非 0 失败）
docker compose run --rm verify
echo $?        # 0 = 全部通过
```

`verify` 服务自包含（独立安装依赖、测试、构建并对构建产物做 HTTP 冒烟），不依赖 `app` 服务。

## 项目结构

```
├── Dockerfile              # 多阶段：build / verify / app（默认）
├── docker-compose.yml      # app（端口可配 + 健康检查）与 verify（一次性）
├── nginx.conf              # SPA 回退 + /healthz + 静态资源缓存
├── scripts/
│   ├── verify.sh           # 测试 → 构建 → 冒烟，退出码报告结果
│   └── smoke.mjs           # 静态站点 HTTP 冒烟（零依赖 Node 脚本）
├── src/
│   ├── core/
│   │   ├── edmonds.ts      # Chu-Liu/Edmonds 最小有向生成树（bigint 复合权重）
│   │   ├── solve.ts        # 字典序扰动编码、父链路/路径/累计代价组装、可达性
│   │   ├── validate.ts     # 字段级校验（一次性收集全部错误）
│   │   ├── import.ts       # 导入解析
│   │   └── sample.ts       # 内置示例（含贪心成环与字典序裁决场景）
│   ├── components/         # 节点/链路编辑器、导入面板、反馈面板、结果面板
│   └── App.tsx             # 状态编排：输入变更立即使旧结果失效
└── tests/                  # vitest：算法单测 + 暴力枚举对拍 + 校验规则
```
